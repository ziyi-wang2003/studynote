## vLLM：面向高吞吐量大模型推理的系统设计

### 1 动机：从算法效率到系统工程

在 Transformer 自回归推理的优化历程中，FlashAttention 系列致力于解决 **单请求内部的注意力计算效率**，通过 IO 感知的算法设计大幅降低了单次前向计算的内存访问开销。然而，现代 LLM 服务场景的核心挑战远不止于此——系统需要同时处理来自数千个用户的并发请求，每个请求具有不同的输入长度、输出长度和到达时间。在这种多请求并发环境中，真正制约吞吐总量的瓶颈往往来自三个方面：**KV Cache 内存管理的粗放性**（内存碎片与显存浪费）、**批处理策略的刚性问题**（因等待慢请求而导致的 GPU 空闲）以及 **Prompt 计算的重复性**（不同请求共享相同前缀时的冗余计算）。

vLLM 是一个专为高吞吐量 LLM 服务设计的推理框架，其核心贡献在于**将操作系统级别的虚拟内存与分页管理思想引入大模型推理系统**。vLLM 的工作始于 2023 年 SOSP 论文《Efficient Memory Management for Large Language Model Serving with PagedAttention》，在随后的发展中持续演进，目前已成为业界广泛部署的高性能推理后端。该框架与 FlashAttention 的分工明确：FlashAttention 聚焦于**单请求内的注意力计算内核优化**，而 vLLM 则着力于**请求间的系统级资源调度与复用**。二者在部署时通常协同工作，共同构成高吞吐量推理服务的核心技术栈。

本章将依次剖析 vLLM 的三个核心机制——**PagedAttention**（分页注意力，解决内存碎片与过度预留问题）、**Continuous Batching**（持续批处理，解决静态批处理的低效等待问题）以及 **Automatic Prefix Caching**（自动前缀缓存，解决前缀重复计算问题），并阐释它们之间如何协同运作，共同实现数量级的吞吐量提升。

![vLLM PagedAttention 与持续批处理系统图](/static/images/uploads/大模型显存优化/vllm-pagedattention-scheduler.png)

图中把 vLLM 的三项机制统一到“KV 块”抽象上：PagedAttention 用块表把每个请求的逻辑块映射到非连续的物理块池，减少连续预留和碎片；Continuous Batching 在每个 decode step 动态移除已完成请求并接纳新请求，让 GPU 计算槽位持续被填满；Automatic Prefix Caching 通过哈希表和引用计数复用相同前缀块，分支生成时再用写时复制处理不同后缀。

### 2 经典 KV Cache 的内存管理困境

#### 2.1 内存碎片与过度预留

在没有专门优化的情况下，KV Cache 通常被组织为连续的数组，每个请求预分配一块与其最大生成长度相匹配的连续显存区间。这种方案面临两个相互关联的问题：

**预留碎片**（Reservation Fragmentation）：系统难以确切预知每个请求的最终生成长度。为安全起见，通常按照最大可能长度（如 max_tokens）进行预留。若请求实际生成较短，大量预留但未使用的显存被浪费；若请求超过预期，则可能面临内存不足（OOM）风险。

**内部碎片**（Internal Fragmentation）：即使每个请求的预留长度恰好等于实际生成长度，不同请求的 KV Cache 也需要在显存中连续存放。当请求完成释放后，其留下的空隙通常只能被长度相同或更短的新请求复用，形成不可重利用的碎片空间。实验数据显示，在典型的工作负载下，经典的连续内存分配方案可能浪费高达 60%-80% 的显存。

#### 2.2 两阶段推理的批处理限制

推理过程分为 **Prefill 阶段**（并行处理输入 prompt 的全部 token）和 **Decode 阶段**（逐 token 生成输出）。在 Prefill 阶段，GPU 计算资源高度饱和；而在 Decode 阶段的每一步，每个 token 仅需计算一次前向传播，算术强度（计算量 / 内存访问量）较低，处于典型的内存受限状态。传统的静态批处理策略要求一个批中的所有请求同时开始、同时结束，这意味着整个批处理的吞吐量由批中最慢的请求决定——一旦某个请求进入较长的解码阶段，其他已完成的请求必须等待，造成 GPU 闲置。

### 3 PagedAttention：分页内存管理

#### 3.1 核心思想：从连续分配到分页块

PagedAttention 借鉴操作系统虚拟内存的分页思想，将每个请求的 KV Cache 划分为固定大小的 **KV 块**（KV Block）。每个 KV 块包含固定数量 token 的注意力键和值。块大小可根据配置设定（典型值为 16 或 32）。这些 KV 块在物理显存中**无需连续存放**；每个请求维护一张 **块表**（Block Table），记录其逻辑块序列与物理块的映射关系。这种设计使得按需分配成为可能——系统仅在请求实际扩展时才为其分配新的内存块，而非预先预留整个最大长度的连续区域。

vLLM 为每个请求维护 **逻辑块列表**（logical blocks），表示该请求在序列长度维度上需要哪些块。与此同时，**物理块池**（physical block pool）管理实际的显存区域。块表的作用正是将逻辑块索引映射到物理块地址。当一个新的 KV 块需要分配时，vLLM 从物理块池中选取任意空闲的物理块，记录在块表中；当完成某个块之后，该物理块被返还给块池以供复用。

#### 3.2 KV 块的哈希与全局复用

为了实现跨请求的 KV 块复用，vLLM 为每个 KV 块维护一个 **哈希签名**，该哈希由**该块内部的所有 token 以及该块之前的所有前缀 token** 共同决定。举例而言，对于一个作为系统提示词的长文本，它可能跨越多于一个块的范围：这些块中的哈希值不仅取决于块内的 token，还取决于此前所有前缀块的 token。。

所有物理块的哈希键值被维护在一个 **全局哈希表** 中，具有相同哈希值的块可被映射到同一块物理内存区域，从而在不同请求间实现共享。当一个新请求到达时，vLLM 逐个块地计算其哈希值，并检查全局表中是否存在相同哈希的块。若存在，则该块无需重新计算 KV Cache，直接复用现有物理块，只需将该请求的块表指向该物理块并增加其引用计数；若不存在，则分配新块并将哈希键值及对应的块插入表中。这种哈希驱动的设计实现了 **自动前缀缓存**，无需维护复杂的块间树结构或要求请求具有严格的对齐边界。



#### 3.3 块级共享与 Copy-on-Write

vLLM 的块级共享不仅被用于前缀缓存，同样支持并行采样（parallel sampling）场景下的内存优化。例如，当同一个 prompt 同时生成多个不同的响应时，请求之间在 prompt 部分共享完全的 KV 块。然而，一旦某个分支开始生成第一个不同的 token，其后续的 KV 块将无法继续共享。此时，vLLM 采用 **写时复制**（Copy-on-Write）机制：共享的块维持低引用计数，当某一分支需要写入不同于其他分支的内容时，系统分配新的物理块，复制原有数据并执行写入操作。这一策略在语义上近似于内存页面的写时复制，在不引入额外同步开销的前提下有效减少了重复存储。

#### 3.4 内核实现概要

PagedAttention 的内核（位于 `csrc/attention/attention_kernels.cu`）是实现从分页存储结构中高效读取 KV 数据的关键组件。与标准注意力内核假设 KV 张量在物理上连续不同，PagedAttention 内核需要通过块表查找机制间接访问 KV 数据——每个序列被表示为 `num_seq` 个查询 token 的结构体，每层 **模型**（layer）的 KV 缓存被划分为多个块，内核从一个线程组（thread group）中，从这些块中将指定索引位置的元数据读取至共享内存，然后进行 Query-Key-Value 的矩阵乘法操作。由于 vLLM 的注意力内核与 FlashAttention 针对不同的硬件架构进行过针对性调优，二者在实际生产部署中往往各自发挥优势，而非互相替代。

### 4 Continuous Batching：动态请求调度

#### 4.1 静态批处理的局限

在早期的 LLM 服务系统（如 HuggingFace Transformers 的朴素批处理）中，一个批次的请求被整体提交给模型，只有当该批次中**所有**请求都完成解码阶段后，系统才会处理下一批请求。这造成了两个层面的低效率：

- **等待空闲**：执行速度快的请求已完成解码，由于需要等待同批次中的慢请求，GPU 必须保持空闲。
- **批大小僵化**：在静态批处理中，批大小在批建立之初就已固定，无法在批次执行过程中容纳新到达的请求。新到达的请求必须等待整个批次结束后才能获得服务，增加了排队延迟。

#### 4.2 持续批处理调度器

vLLM 采用了 **持续批处理**（Continuous Batching）调度器。该调度器不要求在批次开始前确定请求集合，而是**在每一步解码迭代中动态决定当前批次应当包含哪些请求**。调度器的核心流程如下：

1. **迭代级别调度**：在每个解码步骤开始时，调度器检查运行中的请求状态。当一个请求完成生成（如遇到 EOS token 或达到最大长度限制）时，该请求被移除，其占用的 GPU 计算槽位被立即释放。
2. **队列注入**：释放出的槽位可用于接纳等待队列中的新请求。新请求的 prompt 部分需要经过 Prefill 阶段；对于采用了前缀缓存的请求，其 Prefill 开销可显著降低。
3. **约束条件**：调度器受限于 GPU 显存容量（即 KV Cache 总量）、`max_num_seqs`（最大并发序列数）和 `max_num_batched_tokens`（每批次最多的 token 总数）。调度器在这些约束下尽可能多地接纳等待队列中的请求，最大化 GPU 占用率。
4. **Prefill 与 Decode 的调度权衡**：Prefill 阶段的计算量远高于单个 Decode 步骤。若在同一个批次中同时包含 Prefill 请求和解码请求，必须确保二者计算量合理分配，以避免 Prefill 请求独占过多计算资源而严重延长解码延迟。vLLM 的调度策略在 v1 版本中引入了 **分块预填充**（Chunked Prefill），将长 prompt 拆分为多个小块与解码请求交叠执行，在吞吐量与首 token 延迟之间实现更优平衡。

#### 4.3 持久化批处理优化

为了降低模型执行器在每次迭代中重构批处理输入张量（如 block table、temperature 等）的 CPU 开销，vLLM V1 引入了 **持久化批处理**（Persistent Batch）优化。其核心观察是：连续解码步骤之间的请求集合变化很慢——通常每一步仅有少数请求加入或完成。与其在每一步都从零构建输入张量，不如维护**持久的状态张量**并仅对差异部分进行增量更新。

在 vLLM V1 的实现中，持久化批处理通过将持久化状态与输入张量耦合来达到高效率，但这种耦合也导致了复杂的请求重排逻辑和维护冗余请求状态的负担。在 **Model Runner V2**（MRV2）中，vLLM 将持久状态张量与每步的输入张量解耦，采用预先分配固定行数的 GPU 输入表，为每个活跃请求永久分配一行，通过 GPU 之上的收集来构建每步的实际输入。这种设计显著降低了 CPU 开销并简化了异步场景下的簿记逻辑。

### 5 Automatic Prefix Caching：自动前缀缓存

![paste_1777887044397.png](/static/images/uploads/paste_1777887044397.png)

#### 5.1 动机：跨请求的前缀共享

在多轮对话或批处理生成应用中，多个请求常常共享相同的语义前缀。对于大语言模型的 API 调用，最常见的复用情况包括：

- **系统提示词**（System Prompt）：一个服务提供的固定的系统级指令，在所有用户请求中的位置均在对话上下文的最前端，形式却完全一致。
- **少样本示例**（Few-shot Examples）：在 prompt 中嵌入的若干个示例问答对，它们在不同请求中完全相同。
- **多轮对话的历史上下文**：在会话场景中，相同用户在同一会话中的后续请求会包含之前历史对话的记录——当会话轮数较长时，这些长前缀的计算量相当可观。
- **Agent 工具定义与说明**：当 LLM 代理系统使用相同的工具集描述时，这些结构化描述不同请求间完全一致。

如果每个请求独立计算这些 token 的 KV Cache，既消耗计算资源，又占用大量用于缓存的显存。前缀缓存的本质，正是**跨请求复用已计算的 KV 块**。

#### 5.2 基于哈希的缓存设计

vLLM 的前缀缓存与 PagedAttention 的块级共享共享同一套基础设施：同一 PagedAttention 的哈希表和物理块池。当一个全块（即足额的块）的所有 token 已被计算时，其哈希值与物理块被记录在全局表中；当下一个请求包含相同的字节序列时，该序列分割为若干个全块，这些块在哈希表中命中，随即发生物理块复用，无需重新计算。

在 vLLM v1 的实现中，核心数据结构位于 `/v1/core/kv_cache_utils.py` 中的 `KVCacheManager` 内。每个块由其块 ID（`block_id`）和哈希值标识。在缓存操作（`allocate`、`append`、`free`、`evict`）中，系统统一通过哈希查找进行索引，对所有共享请求记录**引用计数**（reference count），并在没有空闲块时根据策略淘汰块。


#### 5.3 淘汰策略与性能权衡

由于 KV Cache 的总显存空间有限，当缓存占满时必须决定淘汰哪些块以提高命中率。vLLM 实现了一个 **引用计数 + LRU** 的淘汰策略。该策略可形式化为[6†L38-L45]：

**淘汰规则**（按优先级从高到低）：
1. 选出所有**引用计数**（refcount）为零的块（即当前没有任何活跃请求正在使用）。
2. 若有多个零引用块，选择其中**最近最少使用**（LRU）的块，淘汰之。
3. 若多个 LRU 块的最后访问时间相同，则淘汰位于**最长前缀末尾**的块（即前缀块数量最多的块）。

这个策略的一个关键特性是，它实际上**等价于在完整注意力（full attention）模型中实现的内存高效的 RadixAttention 淘汰策略**——优先淘汰前缀树中的叶子节点（引用计数为零、没有子节点的块），并以 LRU 次序优先淘汰。

**块大小权衡**：块大小（例如 block_size 参数，默认值通常为 16 或 32）直接影响缓存效率和内存密度。更小的块可以捕获更细粒度的前缀复用，提高命中率，但会增加元数据开销和调度复杂程度；更大的块可提高内存带宽利用效率并在物理上减少内部碎片，但其对长前缀对齐的要求更严格，可能导致原本非块边界匹配的块虽然仅差几个 token 就无法复用，整体命中率下降。

**哈希碰撞考**：默认情况下（v0.11 及以后）vLLM 默认使用 SHA-256 哈希函数，理论上保证了无哈希碰撞的安全性。若将哈希算法配置为 xxHash（一种非加密型但更快的哈希函数），虽然匹配速度有所提升，但在多租户环境中会带来碰撞后返回错误 KV 块的风险。为安全隔离多租户缓存，vLLM 还支持配置每请求的 `cache_salt` 参数，将 salt 混入哈希中，从而**隔离不同租户之间的缓存**，使同一物理块池中的块只能在相同 salt 的请求间共享。

### 6 综合性能收益

以上三项机制协同作用，使 vLLM 能够在高并发环境下实现远超传统实现的吞吐量。在公开的基准测试中，vLLM 对比 HuggingFace Transformers 的吞吐量提升可高达 **24 倍**，对比 Text Generation Inference（TGI）的吞吐量提升约为 **3.5 倍**。连续批处理消除了静态批等待的低效，使 GPU 在解码阶段始终有请求可处理。PagedAttention 将显存利用率提升了多个数量级，使得在固定显存容量下可同时服务的并发请求数大幅增加。前缀缓存进一步将相同前缀的计算量降至接近零，在系统 prompt 较长的场景中带来首 token 延迟的显著降低。

vLLM 的设计对 **LLaMA、Mixtral、Qwen** 等主流开源模型提供了开箱即用的支持，并与 FlashAttention 内核兼容（当 `use_v2_blocked_kv_cache=False` 时可采用 FlashAttention-2/3 内核执行注意力计算，从而实现单请求内上的 IO 效率与系统调度层效率的双重优化）。随着 vLLM v1 引擎的持续演进，当前的代码主干已大量采用 Rust 重写的高效调度逻辑与异步处理框架，进一步逼近硬件性能极限。

### 7 总结

vLLM 将传统的独立批次处理风格替换为系统级资源管理层，通过 **PagedAttention** 的内存分页管理、**Continuous Batching** 的请求动态调度，以及 **Automatic Prefix Caching** 的块级缓存共享三大核心设计，解决了大模型服务中 KV Cache 碎片化与过度预留、批处理均匀性差、前缀重复计算三个关键问题。这三个组件的统一抽象源自 **块**（block）和 **哈希表**——PagedAttention 用块管理与间接索引解决了内存碎片问题；连续批处理借由块粒度的资源释放/重建实现无缝的请求进出；前缀缓存则在全局哈希表中追踪块的内容和前缀，由此实现跨请求的自动复用。对深入大模型服务系统优化的研究者与工程师而言，vLLM 提供了一种从内存管理视角重塑推理服务架构的范式——这正是在大模型时代将单一模型能力扩展为工业级服务能力的基础性基础设施。
