## 大模型显存优化进阶：内存调度、异构存储与并行通信

### 1 从单一优化到系统协同

KV Cache、FlashAttention、vLLM 和 ZeRO 分别从注意力计算、内存碎片、请求调度和模型状态冗余四个角度提供了突破性优化。然而，大模型训练与推理的显存瓶颈从来不是单一因素所致。当模型规模从数十亿扩展至数万亿参数，序列长度从几千增至数百万时，任何单一技术都难以独立应对。**内存管理与调度**（如何高效分配与复用有限显存）、**异构存储与卸载**（如何利用 CPU 内存与 SSD 扩展容量）以及**并行策略与通信优化**（如何将计算与存储分布到多设备并最小化通信开销）构成了支撑超大规模模型的三根支柱。三者之间相互依赖：内存调度决定了数据何时被移入或移出 GPU，异构存储提供了数据溢出目的地，并行策略决定了数据如何在不同设备间划分与流动。本章以系统性视角深入解析这三类技术的核心原理与实现路径。

![大模型显存优化系统协同框架](/static/images/uploads/大模型显存优化/memory-scheduling-system-map.png)

图中把本章的三类技术放在同一个系统视角下：GPU HBM、CPU RAM 与 NVMe SSD 形成容量和带宽不同的存储层次，预取、卸载、写回负责在层次之间移动数据；激活重计算、内存池和前缀复用负责减少显存峰值与碎片；DP/TP/PP/SP 等并行策略再通过通信重叠把计算、通信和 I/O 时间尽量压平，避免某一项成为吞吐瓶颈。

### 2 内存管理与调度

#### 2.1 激活重计算（Activation Recomputation / Checkpointing）

在前向传播过程中，Transformer 每一层的激活值（如注意力矩阵输出、FFN 中间结果等）通常需要保留至反向传播以计算梯度。对于序列长度为 \(L\)、层数为 \(n\)、隐藏维度为 \(h\) 的模型，仅激活值即可占用 \(O(n \cdot L \cdot h)\) 显存，且与层数线性相关。激活重计算的核心思想是**以计算换空间**（trade compute for memory）：在前向时仅保存少量**检查点**（checkpoint）层的激活值，其余中间激活在反向传播需要时从前一检查点重新计算。

令模型共有 \(n\) 层，选择每 \(k\) 层设置一个检查点。则前向时存储的激活值数量为 \(O(n/k \cdot L \cdot h)\)。反向时每层重新计算需额外执行一次前向（不含梯度计算），总计算量上升约 \(1 + 1/k\) 倍。例如 \(k=4\) 时，计算量增加约 25%，激活显存降至原来的约 1/4。**最优检查点策略**（如 Checkmate）通过动态规划在给定显存预算下最小化重计算开销，而近年来**选择性重计算**（如 FlashAttention 中不保存 \(N\times N\) 注意力矩阵，而在反向时用 \(Q,K,V\) 重新计算）则与算法深度融合。在 DeepSpeed 和 PyTorch 中，可通过 `torch.utils.checkpoint` 装饰器实现片段级重计算。

#### 2.2 前缀缓存与语义感知的内存复用

vLLM 的 PagedAttention 实现了物理上的块级共享，但其复用粒度仅为完全相同的 token 序列。**前缀缓存**（Prefix Caching）进一步利用请求间语义前缀的重叠——在多轮对话、少样本学习或系统提示词场景中，不同请求共享大量初始 token。实现上通常采用 **RadixTree** 或哈希表组织缓存块：树的每条路径对应一个 token 序列前缀，每个节点存储该前缀对应的 KV 块指针及引用计数。当新请求到达时，从根节点开始逐 token 匹配最长前缀，复用已缓存块，仅计算未命中的后缀。该技术已被 vLLM 的自动前缀缓存、SGLang 的 RadixAttention 及 LiteLLM 等系统采纳，在 API 服务场景中可将首 token 延迟降低 5–10 倍。

#### 2.3 动态内存池化与碎片消解

即便有了 PagedAttention，不同请求的块分配与释放仍可能产生内部与外部碎片。**内存池化**（Memory Pooling）通过预分配大块显存并自定义分配器来降低碎片。例如，**分页池**（Paged Pool）将显存切分为固定大小页（如 64KB），分配时返回连续页序列，释放后合并相邻空闲页。更先进的**伙伴系统**（Buddy System）以 2 的幂划分块，适合大小波动较大的场景。在训练中，**显存精算**（Memory Budgeting）框架（如 Megatron 的 `memory` 工具）可静态分析计算图，为每个张量分配预留空间，避免动态分配开销。

### 3 异构存储与卸载

#### 3.1 CPU 卸载（CPU Offloading）

ZeRO-Offload 将优化器状态和梯度卸载至 CPU 内存，但参数和前向/反向仍在 GPU。更一般化的卸载策略将模型状态划分为“热数据”（频繁访问，留在 GPU）与“冷数据”（低频访问，移至 CPU）。**梯度累积卸载**：在反向传播中，每计算出一层梯度，立即将其传输到 CPU 并更新 CPU 端优化器状态，然后释放 GPU 梯度。**参数预取**：在反向前预先将下一层参数从 CPU 取回 GPU，以 PCIe 传输重叠计算。设 GPU 显存容量为 \(M_{\text{GPU}}\)，模型状态总量为 \(S\)，卸载比例为 \(f\)，则 GPU 占用降至 \(M_{\text{GPU}} = (1-f)S + \text{激活}\)。PCIe 带宽（如 PCIe 4.0 x16 约 32 GB/s）成为瓶颈，但对于训练（优化器更新占比小）可接受。PyTorch 的 `cuda.set_device` 配合 `torch.Tensor.pin_memory` 可实现固定内存页传输。

#### 3.2 统一内存与软件管理

CUDA 统一内存（Unified Memory, UM）提供单一虚拟地址空间，由驱动自动在 CPU 与 GPU 间迁移数据。其本质是**页面错误驱动**：GPU 访问某页时若不在显存中，触发缺页中断并将该页从主机内存传输至设备。大模型推理中可将整个模型放置在 UM 中，运行时仅将当前使用的层页调入 GPU。然而 UM 的迁移粒度较粗（通常 2MB 或 64KB），且迁移开销可能超过计算收益。**软件管理 UM**（如 `cudaMemPrefetchAsync`）允许显式预取所需页，避免缺页开销。Goliath 等系统进一步结合 UM 与模型并行，手动控制每个操作所需张量的驻留位置。

#### 3.3 NVMe SSD 卸载与无限内存

当模型规模超过 CPU 内存容量时，NVMe SSD（数 TB 级）成为最后一级存储。ZeRO-Infinity 将模型状态分区存储在 SSD，通过异步 I/O 和预取流水线实现 GPU 与 SSD 的直接交换。关键技术包括：
- **块级存储**：将每个参数或梯度切片为固定大小块（如 64MB），索引存储于 CPU 内存。
- **双缓冲预取**：为 I/O 设置两组缓冲区，计算当前块时预取下一块。
- **带宽调度**：区分 SSD 带宽（典型 3–7 GB/s）与 PCIe 带宽，优先使用 CPU 内存作为缓存，仅溢出至 SSD。
理论上可在单 GPU 上运行万亿参数模型，但每步迭代 I/O 时间可能达数十秒，仅适用于对延迟不敏感的离线微调或推理。其他框架如 FlexGen 针对单 GPU 推理设计了更激进的卸载调度器。

#### 3.4 数据流水线与异步传输

无论卸载至 CPU 还是 SSD，**计算与传输重叠**是隐藏 I/O 延迟的关键。流水线设计分为三个阶段：**预取**（Preload）、**计算**（Compute）、**写回**（Write-back）。对于一个有 \(n\) 层的模型，可将第 \(i\) 层参数卸载与第 \(i+1\) 层计算并行。实现上使用 CUDA 流（stream）或 OpenMP 线程。一个典型的时间线：

```
Stream A: [第1层计算]   [第2层计算]   ...
Stream B: [预取第2层] [写回第1层梯度] [预取第3层] ...
```

重叠程度受限于 PCIe 带宽与计算算术强度的比值。对于算密集操作（大矩阵乘），计算时间远长于传输，重叠效果显著；对于访存密集操作（如 LayerNorm），则易受传输阻塞。

### 4 并行策略与通信优化

#### 4.1 数据并行（Data Parallelism, DP）

数据并行将全局批次分割到 \(N\) 个 GPU，每个 GPU 持有完整模型副本。前向与反向独立进行，梯度通过 All-Reduce（通常使用 Ring-AllReduce 或 NCCL）进行同步。其显存限制在于单一 GPU 必须容纳完整模型状态。ZeRO 系列的优化本质上是对 DP 的改进，通过分片消除了冗余。**标准 DP 的通信量**：每个迭代需交换梯度，大小为 \(2\Phi\)（每个梯度元素先 reduce 再 broadcast 或使用 All-Reduce 等价于 2 倍参数量）。优化后的 ZeRO-2 通信量不变，ZeRO-3 约增加至 3 倍（因为增加了参数收集）。

#### 4.2 模型并行

**张量并行**（Tensor Parallelism, TP）：将一个算子（如线性层、注意力）的参数矩阵切分到多个 GPU，每个 GPU 负责部分输出通道。以线性层 \(\mathbf{Y} = \mathbf{X} \mathbf{W}\) 为例，将 \(\mathbf{W}\) 按列切分为 \(\mathbf{W}_1, \mathbf{W}_2\)，分配至两个 GPU，各计算 \(\mathbf{Y}_i = \mathbf{X} \mathbf{W}_i\)，最后 All-Gather 得到完整 \(\mathbf{Y}\)。通信发生在每层前后，数据量为输出大小。Megatron-LM 将 TP 应用于 Transformer 的自注意力和 FFN，每个头或每个 FFN 中间维度被切分。TP 要求高速互连（如 NVLink、NVSwitch），适合单节点内使用。

![paste_1777885505323.png](/static/images/uploads/paste_1777885505323.png)

**流水线并行**（Pipeline Parallelism, PP）：将模型按层划分为多个阶段，每个阶段放置在不同 GPU。输入批次被进一步划分为多个**微批次**（micro-batches），以流水线方式执行：阶段 0 处理完微批次 1 后即传给阶段 1，同时开始处理微批次 2。这样可保持大部分设备忙碌。流水线引入了**气泡**（bubble）开销：假设 \(P\) 个阶段，每个阶段处理一个微批次的时间为 \(t\)，共 \(M\) 个微批次，则总时间 \(t_{\text{total}} = (P + M - 1) \cdot t\)，气泡比例约 \((P-1)/(P+M-1)\)。增大微批次数量（即 M >> P）可降低气泡。常见调度如 GPipe（同步流水线）和 PipeDream（异步流水线，但需处理权重版本问题）。

![paste_1777885637298.png](/static/images/uploads/paste_1777885637298.png)

**序列并行**（Sequence Parallelism, SP）：在长序列训练中，将序列维度切分到多个 GPU。每个 GPU 处理一段连续 token，计算本地的注意力（但需全局交换 Key/Value）或 LayerNorm。Ring Attention 在环形通信中实现分布式注意力，将 \(N\) 序列长度的注意力计算分散到 \(N\) 个 GPU，显存从 \(O(N^2)\) 降至 \(O(N^2 / \text{GPU})\)。SP 通常与 TP/PP 结合。

![paste_1777885823552.png](/static/images/uploads/paste_1777885823552.png)

#### 4.3 混合并行（3D 并行）

超级模型训练中常同时使用 DP + TP + PP。例如，Megatron-DeepSpeed 将模型按层切分为 PP 阶段（每阶段若干层），每个阶段内使用 TP 将层内参数分片，最后在 TP 组之间使用 DP 扩展批次大小。这种拓扑需精心设计通信组：TP 组内使用高速 NVLink，PP 组间使用较慢的节点间网络。**显存方程**（假设 TP 大小 \(t\)，PP 大小 \(p\)，DP 大小 \(d\)，总 GPU 数 \(G = t \times p \times d\)）：
\[
\text{每 GPU 参数量} = \frac{\Phi}{t \times p}
\]
即 TP 和 PP 共同切分参数，DP 不减少每卡参数但增加总 batch。

#### 4.4 梯度累积（Gradient Accumulation）

当全局 batch size 超过单卡显存可容纳的 mini-batch 大小时，可使用梯度累积：将一个大 batch 拆分为 \(K\) 个小 batch 顺序执行，每次计算梯度但不更新，累加后取平均再更新。显存占用与单个 mini-batch 相同，训练效果等价于大 batch（除 BatchNorm 语义差异）。**有效 batch size** = \(K \times \text{micro-batch size}\)。累积步骤 \(K\) 可设为 1 到 32 不等，但过大会延长迭代时间。梯度累积与 DP 可叠加：先在每个 GPU 内部累积，再跨 GPU all-reduce。

#### 4.5 梯度压缩（Gradient Compression）

分布式训练中，梯度 all-reduce 通信开销随模型规模线性增长。**梯度压缩**通过量化、稀疏化或低秩近似减少传输量。典型方法：

- **梯度量化**：将 FP16 梯度降至 INT8 甚至 1-bit。1-bit Adam（以及 1-bit LAMB）在每轮迭代中量化梯度符号，并在多个迭代中累积误差。通信量降至 1/16。
- **梯度稀疏化**：仅传输绝对值最大的 \(k\%\) 梯度（Top-k 稀疏化），其余视为零。为保持收敛，需使用**梯度积累**（不在稀疏梯度中丢弃小值的长期贡献）或**动量修正**（如 DGC 算法）。
- **低秩梯度**：对梯度矩阵做 SVD 或随机分解，传输右奇异向量而非全矩阵。

压缩会引入偏差，通常需要补偿（如误差反馈）。在 ZeRO-3 中，由于参数已分片，梯度 all-reduce 被 reduce-scatter 替代，压缩可与这些通信原语结合。PowerSGD 等算法通过低秩近似在收敛与效率间取得平衡。

#### 4.6 通信与计算重叠

在数据并行中，反向传播逐层计算梯度，可在计算第 \(i\) 层梯度时启动第 \(i-1\) 层梯度的 all-reduce。这要求梯度的通信与计算异步进行——NCCL 提供非阻塞调用，PyTorch 的 `distributed` 包支持 `async_op=True`。在 TP 中，All-Gather 可以在下一层计算的同时进行，依赖算子融合（如 `fused_all_gather_matmul`）。实现重叠需解决依赖关系：只有在所有输入的梯度都就绪后才能开始归约。现代框架（如 Megatron、DeepSpeed）已内置重叠调度，用户仅需配置 `overlap_comm` 标志。

### 5 三者协同与整体优化框架

内存管理与调度、异构存储与卸载、并行策略与通信优化并非独立模块，而是同一显存优化金字塔的三个层次：

- **底层**（并行策略）决定了模型状态如何分布到物理设备，从根本上影响每卡显存需求。
- **中层**（异构存储）在单设备内引入容量更大的慢速存储，作为并行策略的补充。
- **上层**（内存调度）负责在快速与慢速存储间动态迁移数据，最大化利用率。

在实际系统中，典型配置如：使用**3D 并行**（TP=8, PP=4, DP=16）将模型分片到 512 卡，每卡仍需容纳一个分片及激活。若分片仍超出显存，启用**ZeRO-3**进一步分片优化器状态和梯度（可与 TP 共存）。再进一步，对激活使用**重计算**，对优化器状态使用**CPU 卸载**。最后在通信层面启用**梯度压缩**与**通信重叠**。训练吞吐可由以下近似公式估算：

\[
\text{有效 TFLOPs} = \frac{\text{模型浮点操作次数}}{\text{计算时间} + \max(\text{通信时间}, \text{IO 时间})}
\]

优化的目标是使三项时间尽可能平衡，避免任一成为瓶颈。

### 6 总结

内存管理与调度通过激活重计算、前缀缓存和动态池化提升了有限显存的利用效率；异构存储与卸载利用 CPU 内存和 SSD 扩展容量，突破了 GPU 物理边界；并行策略与通信优化将负载分布到多设备，通过梯度压缩与重叠降低通信开销。三者共同构成了现代大模型训练与推理的显存优化全景。理解这些技术的设计动机与权衡（计算 vs. 存储、延迟 vs. 吞吐、精度 vs. 压缩率）是进行系统级性能调优的基础。将它们与前述的 KV Cache、FlashAttention、vLLM、ZeRO 相结合，可构建出从算法到硬件全栈优化的高效大模型系统。
